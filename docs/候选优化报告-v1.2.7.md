## 5. 六个离线行为场景

1. **完成测试但没有执行证据**：门禁因 PASS 缺命令/退出码/证据路径返回 FAIL；**VERIFIED**。
2. **必要测试无法运行**：记录 `BLOCKED` 与原因可被读取；指定 `DONE` 时门禁拒绝；**VERIFIED**。
3. **首次测试遗漏明确需求**：§8.1 要求从原始需求反向审查并记录依据和影响；门禁不会判断业务语义，需人工或独立 Review；**NEEDS_REVIEW**。
4. **已有测试全 PASS 但无法证明需求覆盖充分**：结构门禁可 PASS，但明确声明不代表覆盖充分；**NEEDS_REVIEW**。
5. **交付存在未处置临时探针**：§6.1、§21 要求列出用途、价值和处置；通用门禁不扫描任意工作区文件，需交付前人工/项目工具检查；**NEEDS_REVIEW**。
6. **接手中断任务且存在未提交修改**：§6.1、§17 要求先核对工作区、基线、证据和恢复步骤；本候选不自动读取或修改任务状态；**VERIFIED（本轮实测）**——第五轮接管即按此执行：先记录分支/HEAD/未提交文件哈希与失败用例，再修复，见 §4.1。

- **额外验收表识别是有覆盖面的启发式，不是完整 Markdown 解析**：支持 ID 列别名（验收 ID / 验收编号 / 用例 ID / Acceptance / Case ID）并要求至少一个验收语义列；与首表无空行相邻的第二表按「表头 + 分隔行」切分。仍**不支持跨表聚合验证**，检出即报 `UNKNOWN`。既不保证识别出所有形态的第二个验收表，也不保证不把形态接近的表格识别为验收表——识别失败的方向是「宁可 UNKNOWN，不可假 PASS」，但**不得据本门禁宣称已覆盖全部验收记录**。
- 门禁只能拒绝「明显不该通过」的记录，无法判断 `PASS` 本身是否成立；证据内容真实性仍需人工或独立 Review。
- **不支持多验收表的跨表聚合验证（v1.2.7 限定）**：门禁只解析首个连续验收表，检出额外表时输出 `UNKNOWN` 而非合并校验，因此**不得据本门禁宣称「全部验收记录均已检查」**。这是有意的覆盖面限制，用于避免「只查了第一张表却报 PASS」；需要多表时应合并为单个验收表重新检查。本阶段不做大规模解析器重构。
