# Vibecoding 规范 v1.2.8 候选

版本：1.2.8 候选｜更新：2026-11-02｜适用：Codex / Claude Code / 其他遵守仓库入口规则的 Agent

> 一套规范、一个任务真值源、多个 Agent 共用。不安装程序，不直接修改任何业务仓库。

**最推荐的接入方式：在业务项目里把本仓库地址或正式 ZIP 直接交给 Agent，让它按 [《Agent 接入指南》](docs/Agent接入指南.md) 自主完成首次配置与验证。** 之后正常派任务即可，无需每次重复提醒。

## 二、使用原则

1. **项目根 `AGENTS.md` 是跨 Agent 规则入口**。它指向本规范与项目自身的 Spec、架构、任务板、测试命令与约束。优先复用仓库已有路径与制度，不复制第二份任务表。
2. **两个 Agent 的入口机制不同**：Codex 原生读取 `AGENTS.md`；Claude Code 由「Project instructions」设置决定 —— 默认只在**工作目录及其上方都没有 `CLAUDE.md` 类文件**时才读取 `AGENTS.md`。⚠ 因此**只检查项目目录是不够的，上方任意一层有 `CLAUDE.md` 就会让 `AGENTS.md` 静默失效**。需要两者共存时，把该设置改为 `claude-md-and-agents-md`，或让 `CLAUDE.md` 首行 `@AGENTS.md` 导入。完整规则、证据分级与验证方法见 [`agents/Claude-Code.md`](agents/Claude-Code.md)。
3. **实际是否遵守规范，取决于 Agent 是否读取到项目入口与相关文件**；仅放置文件夹不会自动让所有工具遵守规则。接入后请用一次真实任务验证。
4. **不批量把模板复制到所有项目**，也不为格式整齐强行迁移旧代码与文档。**先试点一个任务，验证有效后再推广。**
5. 本规范是跨 Agent 通用基线，**不保证所有 Agent 自动加载本文件**；项目接入必须把路径写进相应入口，并用一个真实任务验证。

## 三、快速开始

### 开始任务

1. 读适用的 `AGENTS.md`（含将修改目录的局部规则），检查工作区、分支与已有修改。
2. 找唯一任务来源，确认目标、范围、依赖与验收。
3. 按需读 Spec、架构、ADR 与相关代码，确定必要验证。
4. 在授权范围内开始；关键需求缺失时记录问题，继续独立可做的工作。

### 发生变更

| 情况 | 处理 |
| --- | --- |
| 用户提出新要求 | 更新受影响的范围与验收，再执行 |
| 公共接口或架构变化 | 检查契约、消费者与 ADR 是否需更新 |
| 测试无法运行 | 记 `NOT_RUN` |
| 前置条件阻断验收 | 记 `BLOCKED` |
| 任务取消 | `CANCELLED`（或项目原生取消机制），保留原因与已产生改动 |

### 从中断恢复

核对任务最新内容 → 工作区 diff → 证据版本 → 未完成验收 → 下一步。
可能产生重复外部效果的操作，**先查实际结果再决定重试**。

### 结束任务

检查 diff、实际验证与必要验收 → 适用时从原始需求和风险执行一次反向遗漏审查 → 同步受影响文档 → 记录证据与交接 → **检查本次产生的临时文件与探针能力沉淀**（复用集成 / 清理 / 正式化 / 归档 / 记录，见母规范 §21）→ 仅在 DoD 全部满足后标 `DONE`。
交付状态需区分：代码完成 / 已提交 / 已合并 / 已发布。

### 最小文档规则

- 只修内部小 bug：任务记录 + 验证记录通常足够。
- 需求改变 → Spec；结构改变 → architecture；重要决策 → ADR。
- 不为一次改动更新全部文档，不创建重复任务表。

## 四、接入到你的项目

> **建议首次接入直接按照 [Agent 接入指南](docs/Agent接入指南.md) 操作。**以下为快速检查清单；请勿把本段和接入指南当成两套独立的强制规则。

### 4.1 放到本地

本包是 **Markdown 工程规则与模板**，不是可执行插件；解压后不会自动配置 MCP、Skills 或修改任何代码仓库。

1. 下载 `Vibecoding规范-v1.2.8-候选-完整整合版.zip`。
2. 先备份本地已有同名目录（如有），**不要直接覆盖未提交的个人修改**。
3. 解压到目标位置。ZIP 内含单一顶层目录 `Vibecoding规范/`：

```powershell
Expand-Archive -LiteralPath "$HOME\Downloads\Vibecoding规范-v1.2.8-候选-完整整合版.zip" -DestinationPath 'D:\work'
```

> **不要**解压到已经命名为 `Vibecoding规范` 的文件夹中，否则会形成双层同名目录。

### 4.2 接一个新项目

- [ ] 确认目标、使用者、范围、非目标与技术约束。
- [ ] 按规模选文件；**只复制需要的模板**。
- [ ] 填写 `AGENTS.md` 的真值源映射、规范路径、修改边界与验证入口。
- [ ] 若使用 Claude Code：确认 `AGENTS.md` 能被读取（见上文原则 2）；已有 `CLAUDE.md` 则增量合并、不覆盖。
- [ ] `README` 提供可用的快速启动与文档链接。
- [ ] `development` 填写实际环境、启动、测试、构建命令及工作目录。
- [ ] 建立唯一任务表，首个任务具备 Owner、验收与验证方法。
- [ ] 复杂需求建 Spec；重要技术决定建 ADR。
- [ ] 约定临时文件与工作区卫生做法（隔离目录如 `.agent-scratch/<任务 ID>/`、忽略策略、DONE 前检查）。
- [ ] 删除无用章节；检查所有占位符，未知值标为待确认。
- [ ] 实际执行一次启动与相关测试，记录 `PASS / FAIL / BLOCKED / NOT_RUN`。
- [ ] 完成一次任务的 `REVIEW → DONE`，并记录证据与交接。

### 4.3 接一个现有项目

- [ ] 读取当前 `AGENTS.md` 与局部规则，检查工作区与分支。
- [ ] 盘点现有任务表、架构、Spec、ADR、验收与进度文档。
- [ ] 建立「信息类别 → 唯一权威路径」映射。
- [ ] **复用已有命名与任务系统，不创建并行真值源**。
- [ ] 找出过期或互相冲突的状态，依据实际代码与验证修正。
- [ ] 按缺口引入模板；不重写已有有效资料。
- [ ] 为未执行验证明确标 `NOT_RUN`，不沿用历史测试数字。
- [ ] 用一个真实任务验证读取、执行、验收与交接流程。

### 4.4 初始化验收

新 Agent 应能回答：项目目标是什么？当前任务在哪？允许改哪里？验收标准是什么？如何验证？证据在哪里？下一位从哪里继续？

## 五、校验与升级

- `MANIFEST.sha256` 列出发布包内全部文件的 SHA-256（不含清单自身，也不含 `_archive/`、`_review_*/`、`_dist/`）。
- 校验：`python tools/verify_manifest.py` 和 `python tools/check_links.py`；证据模板可用只读 `python tools/check_evidence.py <evidence.md> --task-id <TASK-xxx> --task-status <REVIEW|DONE|IN_PROGRESS|BLOCKED>` 检查。检查 `DONE` 时还需用任务权威来源提供必要 `--acceptance-id`，否则输出 `UNKNOWN`。省略 `--task-status` 时门禁不判 `PASS`，输出 `UNKNOWN` 并声明未执行 DONE 完整性检查；验收行或总结论为 `FAIL` 时判 `FAIL`。退出码 0=PASS、1=FAIL、2=UNKNOWN，严重度为 `FAIL` > `UNKNOWN` > `PASS`。相对证据路径以证据文件目录为基准，外部索引无法本地验证时输出 `UNKNOWN`。未完成记录不呈现为通过：验收行 `NOT_RUN`/`BLOCKED` 且原因有效时，非 `DONE` 输出 `UNKNOWN`、`DONE` 判 `FAIL`；总结论 `NOT_RUN`/`BLOCKED`/`N/A` 同理；必要验收的 `N/A` 判 `FAIL`。门禁只解析首个连续验收表，不支持跨表聚合验证，不应据此宣称已覆盖全部验收记录。识别边界固定为三档：正式验收表（六类列齐全）全量检查；缺表头分隔行、位于主表之前或列数不足的疑似验收表一律输出 `UNKNOWN` 并给出行号（不得静默忽略，静默忽略即等于假 `PASS`）；普通设计清单与代码示例不参与判定。结果列须为结果语义（`结论 / 结果 / Result / Outcome / 实际`），`预期 / 期望 / Expected / 前置` 属前瞻语义，`用例 ID｜预期结果` 不算执行结论；ID 列支持「验收 ID / 验收编号 / 用例 ID / Acceptance / Case ID」等别名，相邻第二表按表头切分且表头不得被当成数据行；围栏代码块（`` ``` `` / `~~~`）内的表格不参与扫描。额外表内出现 `FAIL` 输出 `UNKNOWN`（不做跨表聚合），但主表中可靠解析出的 `FAIL` 必须判 `FAIL`。报告门禁结论时必须区分「证据结构检查通过」「任务验收通过」与「DONE 完整性判断通过」，不得混为同一结论。重新打包：`python tools/release_zip.py build <输出 zip>`（构建前会强制验证清单与文件哈希）。
- Windows 亦可用 `Get-FileHash -Algorithm SHA256` 校验关键文件。
- 版本号保持在文档与 ZIP 文件名中；**不把目录重命名为 `Vibecoding规范1.2.8`**。
- 新项目可一次性采用；老项目应先试点一个任务，避免批量重构。
- `_archive/` 是历史备份，**不要交给 Agent 当成现行规则**。最新规范始终从 `README.md` / `AI_PROJECT_STANDARD.md` 进入。

> 本次发布包与仓库内工作文件保持同一版本；`_archive/`、`_review_*/`、`_dist/` 一律不打进发布包；当前版本 ZIP 不打包自身（避免无限嵌套）。
